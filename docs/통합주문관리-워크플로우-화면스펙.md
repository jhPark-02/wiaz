# 통합 주문 관리 워크플로우 — 화면 스펙

> **용도:** 데모 구현 및 미팅 시연용
> **작성일:** 2026-07-24
> **전제:** 실연동은 카페24 1채널, 나머지는 동일 화면에 어댑터만 추가
> **관련:** `채널별-API-커버리지.md`, `근거-출처-문서.md`

---

## 0. 이 문서의 원칙

**화면을 실제 API 제약에 맞춰 설계한다.** 지금 "실시간 알림"이나 "전체 기간 조회"를 넣어두면, 연동을 붙이는 시점에 화면을 다시 짜야 한다. 아래 스펙은 전부 확인된 채널 제약에서 역산했다.

미팅에서의 프레이밍도 여기서 나온다 — **"개발이 남았다"가 아니라 "채널사 승인이 남았다"**. 화면은 이미 동작하고, 채널이 늘어도 뒤에 어댑터만 붙는다.

## 1. 전체 흐름

```
[채널 API]
    │ 폴링 5~10분
    ▼
┌─────────────────────────────────────┐
│ 수집 파이프라인                      │
│  ├─ 주문 수집    (주기 스케줄)       │
│  └─ 클레임 수집  (별도 스케줄) ★     │
└─────────────────────────────────────┘
    │
    ▼
[통합주문 DB] ──► ① 대시보드
                  ② 주문 목록
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
    ③ 주문확인   ④ 송장 업로드   ⑤ 주문 상세
          │            │
          └─── 발송처리 ┘
                  │
                  ▼
            [채널 API 전송]
                  │
                  ▼
          전송 결과 기록 (성공/실패/재시도)
```

★ **클레임을 별도 스케줄로 빼는 이유:** 쿠팡은 반품완료건이 발주서 목록에서 조회되지 않아 별도 API를 써야 한다. 주문 목록만 폴링하면 반품 건을 통째로 놓친다. 나중에 붙이는 기능이 아니라 처음부터 분리한다.

## 2. 상태 모델

### 2.1 내부 표준 상태

채널 상태를 그대로 쓰지 않는다. 프론트는 아래 코드만 안다.

| 코드 | 라벨 | 색 |
|---|---|---|
| `NEW` | 신규주문 | 회색 |
| `CONFIRMED` | 주문확인 | 파랑 |
| `READY` | 상품준비중 | 파랑 |
| `SHIPPING` | 배송중 | 파랑 |
| `DELIVERED` | 배송완료 | 초록 |
| `CONFIRMED_PURCHASE` | 구매확정 | 초록 |
| `CLAIM_CANCEL` | 취소 | 빨강 |
| `CLAIM_RETURN` | 반품 | 빨강 |
| `CLAIM_EXCHANGE` | 교환 | 빨강 |
| `DELAYED` | 발송지연 | 주황 |
| `SYNC_FAILED` | 전송실패 | 주황 |

> 채널 상태 수가 크게 다르다. 그립만 33개, 쿠팡·ESM은 클레임이 별도 체계다. **매핑 테이블은 백엔드에 두고, 프론트는 표준 코드만 받는다.** 화면에서 `if (channel === 'coupang')` 분기가 한 번이라도 들어가면 채널 추가마다 프론트를 고쳐야 한다.

### 2.2 발송주체 플래그 ★ 중요

주문마다 **우리가 발송 처리해야 하는지**를 판별하는 필드가 필요하다.

| 값 | 의미 | 해당 |
|---|---|---|
| `SELLER` | 우리가 발송 | 일반 주문 |
| `FULFILLMENT` | 채널/물류사가 발송 | 네이버 도착보장, 쿠팡 로켓그로스, 11번가 슈팅셀러, 토스 도착보장 |

**4개 채널에 존재한다.** 네이버 도착보장은 물류사 시스템이 발주확인·발송처리를 자동 수행하므로 판매자가 별도 처리를 하면 안 된다. 발송 대기 목록에 섞여 있으면 운영자가 계속 처리를 시도하게 된다.

→ 목록에서 **기본 필터로 제외**하거나 뱃지로 명확히 구분.

## 3. 화면 스펙

### ① 대시보드

**목적:** 오늘 처리해야 할 일과 시스템 상태를 한눈에.

**구성**

```
┌── 오늘 처리 ────────────────────────────┐
│  신규주문 12   발송지연 3               │
│  클레임 5      전송실패 1  ← 클릭 시 필터 │
└─────────────────────────────────────────┘

┌── 채널 연동 상태 ───────────────────────┐  ★ 데모 핵심
│  카페24(바디프로젝트)  ● 연결됨          │
│  카페24(일품미식)      ● 연결됨          │
│  11번가                ○ 키 발급 대기    │
│  쿠팡                  ○ 계정 확인 중    │
│  지마켓·옥션           ◐ 승인 대기       │
│  ...                                     │
│  마지막 동기화: 3분 전   [지금 동기화]   │
└─────────────────────────────────────────┘
```

**왜 채널 연동 상태 패널이 중요한가**

미팅에서 ESM 승인 얘기를 자연스럽게 꺼낼 수 있다. 화면에 이미 "승인 대기"로 떠 있으니 별도로 변명할 필요가 없고, 시스템이 그 상태를 관리한다는 인상을 준다.

**키 만료 경고도 여기에.** 쿠팡 API 키는 유효기간이 있고(위아즈 자료상 180일), 홈앤쇼핑은 발급 키가 1년간 유효하다. 만료되면 주문 수집이 통째로 멈추는데 사람이 기억할 리 없다. **D-30 배지**를 띄운다.

**호출 API**
- `GET /orders/counts` — 상태별 건수
- `GET /channels/status` — 연동 상태 + `lastSyncedAt` + 키 만료일
- `POST /channels/{id}/sync` — 수동 동기화

### ② 주문 목록 — 시스템의 본체

**상단 상태 탭 (건수 뱃지)**

```
전체 · 신규주문 · 주문확인 · 배송준비 · 배송중 · 배송완료 · 클레임 · 전송실패
```

카운트는 **현재 필터 조건 기준**이어야 한다. 필터를 걸었는데 탭 숫자가 전체 기준이면 혼란스럽다.

**필터**

| 필터 | 비고 |
|---|---|
| 기간 | **기준일 선택 필수** — 주문일 / 결제일 / 발송일 |
| 거래처 | 다중 선택 |
| 채널 | 다중 선택 |
| 상태 | 탭과 연동 |
| 발송주체 | 셀러발송 / 풀필먼트 (기본: 셀러발송) |
| 검색 | 대상 선택 셀렉트 + 입력창 |

**테이블 컬럼**

```
[✓] 주문일 · 거래처 · 채널 · 주문번호 · 상품명(옵션) · 수량 · 수취인 · 상태 · 택배사/송장 · 결제금액
```

- 가로 스크롤 불가피 → **체크박스·주문번호 열 sticky**
- 상품명 2줄 말줄임 + hover 툴팁
- 행 클릭 → 상세 / 체크박스 → 일괄작업 (**클릭 영역 분리 필수**)
- **주문번호는 문자열로 취급** — 쿠팡 `shipmentBoxId`가 18자리라 숫자로 다루면 JS 정밀도가 깨진다

**일괄 작업 바** (선택 시 하단 고정)

```
주문확인  |  발송처리(송장입력)  |  엑셀 다운로드  |  선택 해제
```

**필수 UX**

- **필터는 URL 쿼리스트링이 단일 소스.** useState로 들고 있으면 상세 갔다 뒤로 왔을 때 날아간다. 운영자는 하루에 수십 번 목록↔상세를 왕복한다
- 페이지 이동해도 **체크 선택 유지** (전체 선택 시 "전체 N건 선택" 배너)
- 무한스크롤 아님, **페이지네이션**
- **서버 페이지네이션 전제.** 클라이언트 정렬 금지

**호출 API**
- `GET /orders?{filters}` — 페이지네이션 메타 포함
- `GET /orders/counts?{filters}`

**쿼리 키:** `["orders", filters]` — filters 객체를 통째로 넣으면 필터 변경 시 자동 갱신되고 이전 결과는 캐시에 남는다.

### ③ 주문확인 — 되돌릴 수 없는 작업 ★

**이 화면이 데모에서 가장 중요하다.** 단순 상태 변경이 아니다.

| 채널 | 부작용 |
|---|---|
| **ESM** | 주문확인 시 배송준비중으로 변경 + 고객 화면에도 표시. **확인 전엔 구매자 취소가 즉시 환불, 확인 후엔 취소 요청이 판매자 승인 방식으로 전환** |
| **그립** | 발주 시 구매자에게 **'배송준비중' 푸시 발송**, 주문취소 불가로 전환 |
| **쿠팡** | 결제완료 → 상품준비중. 취소 건이 섞이면 Partial Error |

**→ 확인 모달 필수**

```
┌─────────────────────────────────────────┐
│  주문확인 처리                           │
│                                          │
│  선택한 24건을 주문확인 처리합니다.      │
│                                          │
│  ⚠ 처리 후에는 되돌릴 수 없습니다.       │
│  ⚠ 고객에게 '배송준비중' 알림이 발송되고,│
│     구매자의 즉시 취소가 제한됩니다.     │
│                                          │
│         [취소]    [주문확인 처리]        │
└─────────────────────────────────────────┘
```

**처리 결과 표시**

부분 성공이 흔하다. 응답을 성공/실패 배열로 받아 결과를 보여준다.

```
처리 완료: 성공 22건 / 실패 2건
  - 주문 20260724-001  이미 취소된 주문입니다
  - 주문 20260724-007  상태가 변경되었습니다
```

**호출 API**
- `POST /orders/confirm` — 부분 성공 응답 형태로

### ④ 송장 업로드 — 2단계 필수

**상태 전이가 강제된다.** 쿠팡은 상품준비중 상태의 주문에만 송장 업로드가 가능하다. **결제완료에서 바로 송장을 넣을 수 없다.** 그립도 택배 정보를 설정해야 발송 요청이 성공한다.

→ 화면 흐름도 반드시 `주문확인 → 송장등록 → 발송처리` 순서.

**흐름**

```
1. 엑셀 업로드
      ↓
2. 검증 결과 미리보기      ← 여기가 핵심
   ┌──────────────────────────────────┐
   │ 성공 45건 / 실패 3건              │
   │                                   │
   │ 실패 내역                         │
   │  행 12  송장번호 중복 (6개월 내)  │
   │  행 27  주문 상태가 맞지 않음     │
   │  행 33  존재하지 않는 주문번호    │
   │                                   │
   │  [실패 건 다운로드]  [45건 확정]  │
   └──────────────────────────────────┘
      ↓
3. 확정 → 채널 전송
```

**검증 규칙 (사전 필터링)**

- **송장번호 중복** — 쿠팡은 6개월 이내 중복 송장번호에서 에러. 단, 수취인 이름과 주소가 같은 다른 주문끼리는 동일 송장 허용 (합포장)
- **상태 확인** — 상품준비중 상태가 아닌 주문 제외
- **주문번호 존재 여부**

**★ 그립은 2회 호출 구조**

그립은 벌크 요청 응답이 `affected`(성공 건수)만 준다. 건별 성패는 같은 요청을 `/result` 경로로 **한 번 더** 호출해야 나온다.

```
PUT /api/delivery/shipping         → affected: 45
PUT /api/delivery/shipping/result  → 건별 성공/실패 + 사유
```

→ 위 미리보기 화면을 그립에서 구현하려면 **반드시 2회 호출**. 백엔드 스펙에 명시.

**호출 API**
- `POST /orders/ship/validate` — 검증만
- `POST /orders/ship` — 확정 전송

### ⑤ 주문 상세

**구성**

```
주문 정보     주문번호 · 채널 · 거래처 · 주문일시 · 상태
수취인·배송지  ⚠ 변경 감지 배지
상품 항목      항목 단위 (부분취소 대응)
결제 정보
처리 이력      타임라인 — 누가 언제 무엇을
채널 원본      접힘 영역
```

**⚠ 배송지 변경 배지 (쿠팡)**

쿠팡은 결제완료 상태에서 고객이 배송지를 변경할 수 있다. **상품준비중 처리 이후 단건 조회로 배송지 변경 여부를 재확인해야 한다.** 수집 시점 주소로 송장을 찍으면 오배송이 난다.

→ 파이프라인에 재조회 단계를 넣고, 변경이 감지되면 화면에 배지.

**처리 이력은 필수.** 누가 언제 어떤 상태로 바꿨는지 남아야 클레임 대응이 된다.

**항목 단위 설계.** 취소·반품은 주문 단위가 아니라 **주문항목 단위**로 발생한다. 그립도 `orderSeq + orderProductSeq` 복합키를 쓴다. 처음부터 항목 단위로 설계하지 않으면 부분취소에서 구조를 다시 짜야 한다.

**호출 API**
- `GET /orders/{id}`

## 4. 화면에 넣으면 안 되는 것

제약에서 자동으로 도출된다. **데모에 넣으면 나중에 못 지킨다.**

| 넣으면 안 됨 | 이유 |
|---|---|
| "실시간 주문 알림" | 쿠팡은 결제완료 후 조회까지 약 10분. 폴링 5~10분이 한계 |
| "과거 주문 전체 조회" | ESM 31일 / 그립 90일 / 카카오 1회 24시간·100건 상한 |
| 발송 대기 목록에 전 주문 | 풀필먼트 4채널은 우리가 발송하지 않음 |
| 채널 무관 단일 상태 필터 | 채널마다 상태 체계가 다름 |
| 낙관적 상태 반영 | 전송 실패 시 화면이 거짓말이 됨. "전송중"이 정확 |

## 5. 프론트 구조

### 5.1 라우팅

```
app/
├─ (dashboard)/
│  ├─ layout.tsx            사이드바 + 헤더
│  ├─ page.tsx              대시보드
│  ├─ orders/
│  │  ├─ page.tsx           목록
│  │  └─ [orderId]/page.tsx 상세
│  ├─ shipping/             송장 업로드
│  ├─ claims/
│  └─ settings/channels/    채널 연동 상태
└─ login/
```

### 5.2 상태 관리

| 종류 | 도구 |
|---|---|
| 서버 데이터 | react-query |
| **목록 필터·페이지·정렬** | **URL 쿼리스트링** (단일 소스) |
| 선택된 행, 모달 | 로컬 useState |
| 사용자·권한 | zustand (최소한으로) |

### 5.3 공통 컴포넌트 (재사용 우선순위 높음)

Phase 1에서 만든 이 셋이 이후 모든 목록 화면(배송·클레임·정산)에 재사용된다. 여기 시간을 더 쓰는 게 전체적으로 이득이다.

- `DataTable` — sticky 컬럼, 선택 유지, 서버 페이지네이션
- `FilterBar` — URL 동기화 훅 포함
- `StatusBadge` — 내부 표준 상태 코드 → 색·라벨

## 6. 데모 구성

### 6.1 시연 시나리오

```
1. 대시보드      오늘 처리할 건수 + 채널 연동 상태 + 동기화 시각
2. 주문 목록     거래처·채널 필터 → 신규주문 탭
3. 일괄 선택     24건 선택 → 주문확인 → 경고 모달 → 처리 결과
4. 송장 업로드   엑셀 → 검증 미리보기(성공/실패) → 확정
5. 주문 상세     처리 이력 타임라인
```

### 6.2 실데이터 vs 목데이터

| 화면 | 데모 시점 |
|---|---|
| 카페24 주문 수집·조회 | **실연동 가능** |
| 11번가 / 쿠팡 | 키 발급되면 실연동, 아니면 목 |
| 나머지 | 목데이터 (연동 상태는 "대기"로 정직하게 표시) |

**목데이터를 쓰는 게 문제가 아니다.** 채널 연동 상태 패널에서 어느 채널이 붙었고 어느 채널이 대기인지 정직하게 보여주면, 오히려 시스템이 그 상태를 관리한다는 신뢰를 준다.

### 6.3 미팅 멘트

> "주문 수집부터 발송처리까지 전 과정이 API로 가능합니다.
> 화면은 채널과 무관하게 동일하게 동작하고, 채널이 늘어도 뒤에 어댑터만 추가됩니다.
> 오늘은 카페24 실데이터로 보여드리고, 나머지는 채널사 승인과 키 발급이 끝나는 대로 같은 화면에 붙습니다."

**"개발이 남았다"가 아니라 "승인이 남았다"** — 정확한 표현이고 사실이다.

## 8. 백엔드 스펙 요청 (데모 이후)
