# 통합 주문 관리 — 프론트 워크플로우

> **전제:** 백엔드가 모든 채널 응답을 통일해서 내려준다. 프론트는 채널별 분기를 하지 않는다.
> **스택:** Next.js 15.5 App Router, TypeScript, Tailwind v4, shadcn/ui, react-query, zustand
> **작성일:** 2026-07-24

---

## 0. 프론트가 지켜야 할 원칙

**화면에서 채널을 판단하지 않는다.** `if (channel === 'coupang')` 같은 분기가 한 번이라도 들어가면 채널이 추가될 때마다 프론트를 고쳐야 한다. 채널은 **표시용 라벨과 필터 값**으로만 쓴다.

대신 **동작이 갈리는 지점은 전부 플래그로 받는다.** 아래 §1의 `canConfirm`, `canShip`, `fulfillmentType` 같은 것들. 이게 없으면 결국 프론트가 채널을 알아야 해진다.

---

## 1. 받아야 하는 데이터 형태

통일된 응답을 가정하고 프론트가 필요로 하는 최소 형태다. **없는 필드가 있으면 이사님께 요청해야 한다.** 각 필드가 왜 필요한지 적어뒀다.

### 1.1 주문

```ts
type OrderStatus =
  | 'NEW'                 // 신규주문
  | 'CONFIRMED'           // 주문확인
  | 'READY'               // 상품준비중
  | 'SHIPPING'            // 배송중
  | 'DELIVERED'           // 배송완료
  | 'PURCHASE_CONFIRMED'  // 구매확정
  | 'CLAIM_CANCEL'        // 취소
  | 'CLAIM_RETURN'        // 반품
  | 'CLAIM_EXCHANGE'      // 교환
  | 'DELAYED'             // 발송지연
  | 'SYNC_FAILED';        // 채널 전송 실패

type FulfillmentType = 'SELLER' | 'FULFILLMENT';

interface Order {
  // 식별자 — 전부 string. 숫자로 받으면 자릿수 큰 채널에서 정밀도가 깨진다
  id: string;
  orderNo: string;
  itemId: string;          // 주문항목 단위. 부분취소가 여기서 일어난다

  partnerId: string;       // 거래처
  partnerName: string;
  channelId: string;
  channelName: string;

  orderedAt: string;       // ISO 8601
  status: OrderStatus;

  productName: string;
  optionName?: string;
  quantity: number;

  receiverName: string;
  receiverPhone?: string;
  receiverAddress: string;

  courierName?: string;
  trackingNo?: string;
  paymentAmount: number;

  // ── 아래부터가 UI 동작을 결정하는 필드들 ──

  fulfillmentType: FulfillmentType;
  //   FULFILLMENT면 우리가 발송 처리를 하면 안 된다.
  //   목록 기본 필터에서 제외하고, 발송 관련 액션을 막는다.

  canConfirm: boolean;
  //   주문확인 가능 여부. 상태만으로 판단하면 안 되는 케이스가 있어서
  //   백엔드가 계산해서 내려주는 게 안전하다.

  canShip: boolean;
  //   송장 등록 가능 여부. 주문확인을 먼저 해야만 되는 채널이 있다.

  addressChanged?: boolean;
  //   수집 이후 고객이 배송지를 바꾼 경우 true.
  //   이 상태로 송장을 찍으면 오배송이 나므로 화면에 경고가 필요하다.

  syncStatus: 'SUCCESS' | 'PENDING' | 'FAILED';
  syncFailReason?: string;
  //   채널 전송 결과. FAILED면 목록에서 눈에 띄게.
}
```

### 1.3 일괄 처리 응답 ★ 중요

**부분 성공이 흔하다.** 전체 성공/실패로 오면 결과 화면을 만들 수 없다.

```ts
interface BulkResult {
  succeeded: string[];              // itemId 목록
  failed: {
    itemId: string;
    orderNo: string;
    reason: string;                 // 사용자에게 그대로 보여줄 수 있는 문구
  }[];
}
```

> **이사님께 요청할 것:** 일괄 처리(주문확인·발송처리·송장업로드) 응답을 위 형태로 통일. `reason`은 채널 원문 에러가 아니라 **한국어로 정규화된 문구**로. 채널마다 에러 형식이 달라서 프론트가 파싱할 수 없다.

### 1.4 상태별 건수

```ts
interface OrderCounts {
  all: number;
  NEW: number;
  CONFIRMED: number;
  // ... 상태별
  SYNC_FAILED: number;
}
```

현재 필터 조건을 반영한 값이어야 한다. 필터를 걸었는데 탭 숫자가 전체 기준이면 혼란스럽다.

### 1.5 채널 연동 상태

## 2. 상태 전이 → 버튼 활성화 규칙

**순서가 강제된다.** 주문확인을 건너뛰고 송장을 넣을 수 없다.

```
NEW ──[주문확인]──> CONFIRMED ──[송장등록]──> READY ──[발송처리]──> SHIPPING ──> DELIVERED
```

버튼 활성화는 **상태로 직접 판단하지 말고 플래그를 쓴다.**

```ts
// ❌ 하지 말 것 — 예외 케이스에서 깨진다
const canConfirm = order.status === 'NEW';

// ✅ 백엔드가 계산한 값을 신뢰
const canConfirm = order.canConfirm;
```

**선택 항목이 섞여 있을 때**

```ts
const selected = orders.filter(o => selectedIds.has(o.itemId));
const confirmable = selected.filter(o => o.canConfirm);

// 일괄 버튼 라벨에 대상 건수를 명시
// "주문확인 (22/24)" — 2건은 대상이 아님을 미리 알린다
```

전부 불가능하면 버튼을 disable하고 tooltip으로 이유를 보여준다.

## 3. 화면별 워크플로우

### ① 대시보드 `/`

**구성**

```
┌ 오늘 처리 ─────────────────────────┐
│ 신규주문 12  발송지연 3            │  ← 클릭 시 해당 필터로 목록 이동
│ 클레임 5     전송실패 1            │
└────────────────────────────────────┘

┌ 채널 연동 상태 ────────────────────┐
│ 카페24(바디프로젝트) ● 연결됨       │
│ 지마켓·옥션          ◐ 승인 대기    │
│ 쿠팡                 ⚠ 키 만료 D-12 │
│                                     │
│ 마지막 동기화 3분 전   [지금 동기화] │
└────────────────────────────────────┘
```

**인터랙션**

- 카운트 카드 클릭 → `/orders?status=NEW` 로 이동 (URL에 필터 실어서)
- `[지금 동기화]` → mutation → 성공 시 `["orders"]`, `["channels"]` invalidate
- 동기화는 즉시 끝나지 않을 수 있음 → 버튼 로딩 상태 + "동기화 요청됨" 토스트

**키 만료 경고**

`keyExpiresAt`이 30일 이내면 경고 배지. 만료되면 주문 수집이 통째로 멈추는데 사람이 기억하지 못한다.

### ② 주문 목록 `/orders` — 중심 화면

**필터는 URL이 단일 소스**

```ts
// useState로 들고 있으면 상세 갔다 뒤로 왔을 때 날아간다.
// 운영자는 하루에 수십 번 목록↔상세를 왕복한다.

const searchParams = useSearchParams();
const filters = useMemo(() => ({
  status:    searchParams.get('status') ?? 'all',
  partnerId: searchParams.getAll('partnerId'),
  channelId: searchParams.getAll('channelId'),
  dateType:  searchParams.get('dateType') ?? 'ordered',
  startDate: searchParams.get('startDate'),
  endDate:   searchParams.get('endDate'),
  fulfillment: searchParams.get('fulfillment') ?? 'SELLER',  // 기본값 주의
  q:         searchParams.get('q'),
  qType:     searchParams.get('qType') ?? 'orderNo',
  page:      Number(searchParams.get('page') ?? 1),
}), [searchParams]);
```

**쿼리 키**

```ts
useQuery({
  queryKey: ['orders', filters],
  queryFn: () => fetchOrders(filters),
  placeholderData: keepPreviousData,  // 페이지 이동 시 깜빡임 방지
});

useQuery({
  queryKey: ['orders', 'counts', filters],
  queryFn: () => fetchCounts(filters),
});
```

filters를 통째로 키에 넣으면 필터 변경 시 자동 갱신되고 이전 결과는 캐시에 남는다.

**상단 탭**

```
전체(48) 신규주문(12) 주문확인(8) 배송준비(5) 배송중(15) 배송완료(6) 클레임(2) 전송실패(1)
```

탭 클릭 → `status` 쿼리 변경. 카운트는 현재 필터 기준.

**테이블**

```
[✓] 주문일 · 거래처 · 채널 · 주문번호 · 상품명(옵션) · 수량 · 수취인 · 상태 · 택배사/송장 · 결제금액
```

- 컬럼이 많아 가로 스크롤 불가피 → **체크박스·주문번호 열 sticky**
- 상품명은 길다 → 2줄 말줄임 + hover 툴팁
- **행 클릭 = 상세 이동 / 체크박스 클릭 = 선택.** 클릭 영역을 반드시 분리 (`e.stopPropagation()`)
- `syncStatus === 'FAILED'` 행은 배경 강조 + 경고 아이콘
- `addressChanged` 행은 수취인 옆에 "주소변경" 배지
- `fulfillmentType === 'FULFILLMENT'` 행은 회색 처리 + "채널배송" 배지

**선택 상태 유지**

```ts
// 페이지를 넘겨도 선택이 유지돼야 한다
const [selectedIds, setSelectedIds] = useState<Set<string>>(new Set());

// 현재 페이지 전체 선택 시 배너 노출
// "이 페이지 20건 선택됨 · [전체 48건 선택]"
```

**일괄 작업 바** — 선택 시 하단 고정

```
22건 선택  |  주문확인(22)  발송처리(18)  엑셀 다운로드  선택 해제
```

각 버튼의 괄호 숫자는 **해당 액션이 실제 가능한 건수**(`canConfirm` / `canShip` 필터링 결과).

**페이지네이션**

무한스크롤 아님. 어드민은 위치 기억과 건수 파악이 돼야 한다.

### ③ 주문확인 모달 ★

**되돌릴 수 없고 고객에게 알림이 나간다.** 채널에 따라 취소 권한 구조까지 바뀐다. 확인 없이 실행하면 안 된다.

```
┌────────────────────────────────────────┐
│ 주문확인 처리                           │
│                                         │
│ 선택한 24건 중 22건을 처리합니다.       │
│ (2건은 이미 처리되었거나 대상이 아닙니다)│
│                                         │
│ ⚠ 처리 후 되돌릴 수 없습니다.           │
│ ⚠ 고객에게 '배송준비중' 알림이 발송되고,│
│    구매자의 즉시 취소가 제한됩니다.     │
│                                         │
│              [취소]  [주문확인 처리]    │
└────────────────────────────────────────┘
```

**낙관적 업데이트 금지**

```ts
// ❌ 실패하면 화면이 거짓말이 된다
onMutate: () => { /* 상태를 CONFIRMED로 미리 바꾸기 */ }

// ✅ 응답 받고 invalidate
onSuccess: (result) => {
  queryClient.invalidateQueries({ queryKey: ['orders'] });
  showResult(result);
}
```

**결과 표시** — 부분 성공을 반드시 보여준다

```
┌────────────────────────────────────────┐
│ 처리 완료                               │
│ 성공 20건 / 실패 2건                    │
│                                         │
│ 20260724-001  이미 취소된 주문입니다    │
│ 20260724-007  상태가 변경되었습니다     │
│                                         │
│                          [확인]         │
└────────────────────────────────────────┘
```

### ④ 송장 업로드 `/shipping`

**3단계 흐름. 검증 없이 바로 전송하지 않는다.**

```
1. 엑셀 업로드
       ↓
2. 검증 결과 미리보기
       ↓
3. 확정 전송 → 결과
```

**2단계 UI**

```
┌────────────────────────────────────────┐
│ 검증 결과                               │
│ 성공 45건 / 실패 3건                    │
│                                         │
│ ┌ 실패 내역 ──────────────────────────┐│
│ │ 행 12  송장번호가 중복되었습니다     ││
│ │ 행 27  주문 상태가 맞지 않습니다     ││
│ │ 행 33  존재하지 않는 주문번호입니다  ││
│ └──────────────────────────────────────┘│
│                                         │
│  [실패 건 다운로드]  [45건 확정 전송]   │
└────────────────────────────────────────┘
```

- 실패 사유는 백엔드가 정규화한 문구를 그대로 표시
- **실패 건만 다시 엑셀로 내려주기** — 운영자가 수정해서 재업로드할 수 있게. 실무에서 가장 자주 쓰는 기능이다
- 성공 건이 0이면 확정 버튼 disable

**전송 중 상태**

```ts
// 확정 후 전송은 시간이 걸릴 수 있다
// 진행률이나 최소한 "전송 중" 표시가 필요
const { mutate, isPending } = useMutation({ ... });
```

### ⑤ 주문 상세 `/orders/[orderId]`

```
┌ 주문 정보 ────────────────────────────┐
│ 주문번호 · 채널 · 거래처 · 주문일시     │
│ 상태 배지                              │
└───────────────────────────────────────┘

┌ 수취인 · 배송지 ──────────────────────┐
│ ⚠ 주소가 변경되었습니다  ← addressChanged
│ 홍길동 / 010-****-**** / 서울시 ...    │
└───────────────────────────────────────┘

┌ 상품 항목 ────────────────────────────┐
│ 항목 단위로 나열. 부분취소 대응        │
└───────────────────────────────────────┘

┌ 처리 이력 ────────────────────────────┐
│ 07-24 14:32  발송처리    김운영        │
│ 07-24 11:05  주문확인    김운영        │
│ 07-24 09:12  주문 수집   시스템        │
└───────────────────────────────────────┘

▸ 채널 원본 데이터 (접힘)
```

**처리 이력은 필수.** 클레임 발생 시 누가 언제 뭘 했는지 증명해야 한다.

**항목 단위 설계.** 취소·반품은 주문이 아니라 주문항목 단위로 발생한다. 처음부터 항목 기준으로 만들지 않으면 부분취소에서 구조를 다시 짜야 한다.

## 6. 로딩 · 빈 · 에러 상태

빠뜨리기 쉬운데 데모에서 티가 많이 난다.

| 상황 | 처리 |
|---|---|
| 최초 로딩 | 테이블 스켈레톤 (행 높이 유지) |
| 페이지 전환 | `keepPreviousData` + 상단 로딩바. 테이블을 비우지 않는다 |
| 결과 0건 | `EmptyState` — 필터 때문인지 데이터가 없는 건지 구분해서 문구 다르게 |
| 조회 실패 | 에러 + 재시도 버튼. 빈 테이블로 두지 않는다 |
| 동기화 진행 중 | 버튼 로딩 + 토스트 |
| 일괄 처리 중 | 버튼 disable + 스피너. **중복 클릭 방지 필수** |

**중복 클릭 방지가 특히 중요하다.** 주문확인·발송처리는 되돌릴 수 없어서 두 번 눌리면 사고다.

## 8. 이사님께 요청할 것

프론트가 이 화면들을 만들려면 응답에 아래가 있어야 한다. 없으면 결국 프론트가 채널을 알아야 해진다.

| 필드 | 없으면 생기는 문제 |
|---|---|
| `canConfirm` / `canShip` | 버튼 활성화를 프론트가 상태로 추측해야 함 |
| `fulfillmentType` | 채널이 발송하는 주문에 발송처리를 시도하게 됨 |
| `addressChanged` | 변경된 주소를 모르고 송장을 찍어 오배송 |
| `syncStatus` + `syncFailReason` | 전송 실패를 화면에 표시할 수 없음 |
| `lastSyncedAt` | "지금 데이터가 최신인가"를 알릴 수 없음 |
| 일괄 처리 **부분 성공 응답** | 성공/실패 결과 화면을 만들 수 없음 |
| 실패 사유 **한국어 정규화** | 채널별 에러 형식이 달라 프론트가 파싱 불가 |
| 식별자 **string 타입** | 자릿수 큰 채널에서 정밀도 손실 |
| 상태별 카운트 (필터 반영) | 탭 숫자와 목록이 어긋남 |

**우선순위:** `canConfirm`/`canShip` → 부분 성공 응답 → `fulfillmentType` 순. 앞의 둘이 없으면 ②③ 화면 자체가 안 나온다.
